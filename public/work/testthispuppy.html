QA in a box: test the real system, then leave no trace.

TestThisPuppy tests a running web application and its real database in one command: the network path, the API, every form, wrong input, SQL injection, race conditions and whole user workflows. Then it puts the database back exactly as it found it. It rebuilds a test harness I first wrote and used at Axis41, Finicity and InComm.

The problem

Most automated tests either mock the database, which tests the mock and not the system, or run against a shared database and leave test rows behind for the next person to trip over. Neither tells you whether the real application, on a real database, behaves when someone types something wrong or something hostile.

Why it is hard

  • Cleaning up. The usual trick, rolling back a test transaction, cannot undo what the application writes through its own database connections.
  • Testing the server, not the browser. A form's own checks hide server bugs, because an attacker simply skips them.
  • Safety. A SQL injection test that works really does drop a table, so it must never touch a real database.
  • Scale. Hundreds of tests are only useful if anyone can add one without writing code.

What it does

  • Two database modes. External connects to an approved test database with credentials and restores it. Internal creates a throwaway PostgreSQL in Docker (Testcontainers), starts the app against it, and deletes it afterwards.
  • Snapshot and exact restore. Every row and id sequence is recorded first. Afterwards, added rows are deleted children first, changed rows set back, removed rows put back parents first, sequences reset, all in one transaction, and a second snapshot must match the first exactly.
  • Checks: connection (resolve, port, SELECT 1, route trace), HTTP, happy path, wrong input with browser checks switched off, SQL injection (throwaway database only), and a race test that fires many requests at the same instant.
  • Workflows as tables. Multi-step macros written by hand or recorded by clicking through the app, repeated as often as you like with fresh Latin dummy data.
  • Log analysis. Stack traces reduced to root causes with secrets hidden, and an optional Claude explanation of each failure.

The proof

  • It found four real bugs on its first run. The demo app saved a customer with an empty name, saved "not-an-email" as an email, crashed on an order for a customer that does not exist, and saved an order with an empty product. All four were hidden by the browser's own checks. They are fixed, and four regression tests pin them; those tests were run against the original code, where they failed, to prove they catch the bugs.
  • 143 of 143 passed in one internal-mode run with each workflow repeated 50 times, including 25 requests fired at once (exactly 25 rows appeared) and 15 SQL injection attacks (every table intact).
  • The database is left exactly as found. In external mode, a real customer and order were untouched, and the next id was still the next id.
  • 54 unit, controller, regression and error-path tests. The error-path tests break things on purpose: a seed that cannot succeed, an unreachable database, a restore blocked partway through (it rolls back completely), an app that dies at start.

Technologies and skills

  • Java 21, Maven, one class per job, plain JDBC for the database work.
  • Spring Boot 3.5 demo app with embedded Tomcat, Spring Data JPA, Thymeleaf, and MockMvc controller tests with Mockito.
  • PostgreSQL 16 schema discovery from information_schema, foreign-key ordering, sequence reset.
  • Selenium WebDriver for page scanning, form filling, macros and a macro recorder.
  • Testcontainers and Docker for throwaway databases; GitHub Actions for CI.
  • Anthropic Java SDK for the optional failure analysis, sent only redacted evidence.
  • AI-assisted engineering. I set the design, the rules and every check; the AI wrote and tested the code under my direction. I am now rewriting three of its parts by hand as practice drills.

What the prompts do not show is the checking. Every claim on this page was run before it was written down, and when a check found a problem (a test that passed for the wrong reason, a safety notice that could be skipped, a regression test that needed proof it could fail), it was fixed before moving on.

What it does not claim

  • It reads PostgreSQL's public schema; other databases need their own schema handling.
  • Every table needs a primary key.
  • The AI analysis is built and tested up to the API call, but needs your own Anthropic credentials and costs money per run.
